Версия: 0.2 (черновик для обсуждения)
Дата: 09.08.2026
Автор: Дамир

## 1. Общие сведения

### 1.1. Назначение продукта
Мобильное приложение и веб-платформа для поиска, найма и оплаты проверенных исполнителей услуг по уходу: няни, бебиситтеры, сиделки для пожилых, помощники для людей с инвалидностью, ситтеры для питомцев.

Референсные продукты: Care.com (США), Rover (США, питомцы), Yoopies (Европа), Helpling (модель верификации).

### 1.2. Проблема
- Поиск нянь и сиделок в РК происходит через знакомых, Instagram, чаты ЖК и агентства.
- Нет проверки исполнителей (несудимость, документы, реальные отзывы).
- Агентства берут высокую комиссию и работают медленно; срочный спрос («няня нужна сегодня вечером», «сиделка после выписки завтра») не закрывается.
- Исполнители не имеют канала стабильных заказов и репутационного профиля.

### 1.3. Целевая аудитория
**Заказчики:**
- Родители детей 0–12 лет (двое работающих, доход средний+), города-миллионники.
- Семьи с пожилыми родственниками, нуждающимися в уходе (в т.ч. проживающие в другом городе — «дети в Астане, родители в области»).
- Семьи с родственниками с инвалидностью.
- Владельцы питомцев.

**Исполнители:**
- Няни и бебиситтеры (студентки педвузов, воспитатели, женщины 35–55).
- Сиделки (в т.ч. с медобразованием).
- Догситтеры и выгульщики.

### 1.4. География запуска
Этап 1: Астана. Этап 2: Алматы. Этап 3: Шымкент, Караганда, остальные города 500К+.

### 1.5. Языки
Русский и казахский — полная локализация интерфейса с первого релиза.

## 2. Роли пользователей

| Роль | Описание |
|---|---|
| Заказчик | Ищет и нанимает исполнителя, оплачивает, оставляет отзыв |
| Исполнитель | Создаёт профиль, проходит верификацию, откликается/получает заказы |
| Модератор | Проверка анкет, документов, споров, отзывов |
| Администратор | Полный доступ: тарифы, выплаты, категории, аналитика |

Один аккаунт может совмещать роли Заказчик + Исполнитель (переключение режима, как в Rover).

## 3. Перечень услуг (каталог)

### 3.1. Вертикаль «Дети»
| Услуга | Формат | Особенности |
|---|---|---|
| Няня постоянная | Полный день / неполный / с проживанием | Долгосрочный контракт, собеседование |
| Бебиситтер | Почасово, разовые заказы | Срочный режим «нужно сегодня» |
| Ночная няня | Ночные смены, новорождённые | Повышенный тариф |
| Сопровождение ребёнка | Забрать из школы/сада, отвести на секцию | Геотрекинг по согласию |
| Няня для ребёнка с особыми потребностями | Почасово/постоянно | Отдельный фильтр квалификаций (опыт с РАС, ДЦП) |

### 3.2. Вертикаль «Пожилые»
| Услуга | Формат | Особенности |
|---|---|---|
| Сиделка почасовая | Разовые и регулярные визиты | |
| Сиделка дневная / с проживанием / 24/7 | Долгосрочно | Договор, график смен |
| Уход после выписки | Краткосрочно (2–8 недель) | Срочный спрос, триггер — выписка из стационара |
| Уход при деменции | Почасово/постоянно | Отдельная квалификация |
| Компаньон | Прогулки, магазин, сопровождение в поликлинику | Низкий порог входа для исполнителей |

**Важно (юридика):** медицинские манипуляции (инъекции, капельницы, перевязки) — лицензируемая медицинская деятельность в РК. В MVP платформа размещает только **бытовой уход и присмотр**. Медуслуги — отдельный этап, только через партнёрство с лицензированными патронажными службами.

### 3.3. Вертикаль «Люди с инвалидностью»
- Помощь в быту, сопровождение, присмотр (взрослые и дети).
- Перспектива: интеграция с госпрограммой индивидуальных помощников (Портал соцуслуг) — отдельное исследование на этапе 2.

### 3.4. Вертикаль «Питомцы»
| Услуга | Формат |
|---|---|
| Выгул собак | Разово / по расписанию |
| Передержка у ситтера | Посуточно |
| Визиты к питомцу на дом | Разово |
| Догситтер на день | Почасово |

### 3.5. Объём MVP
В первый релиз входят: **бебиситтер почасово, няня постоянная, сиделка почасовая/постоянная, компаньон для пожилых**. Вертикаль «Питомцы» — этап 2 (другая механика доверия, проще, но размывает фокус). Вертикаль «Инвалидность» — этап 2–3 после юридической проработки.

## 4. Верификация исполнителей (ядро продукта)

### 4.1. Уровни верификации
Каждый профиль исполнителя имеет публично видимый уровень:

**Уровень 0 — Зарегистрирован** (не показывается в поиске):
- Телефон подтверждён (SMS).

**Уровень 1 — Личность подтверждена:**
- Удостоверение личности РК: верификация через Digital ID (биометрия + документ из eGov mobile / БМГ) — предпочтительный путь; fallback — фото удостоверения + селфи-проверка (liveness).
- ИИН валидирован.
- Возраст 18+.

**Уровень 2 — Проверенный исполнитель (минимум для вертикалей «Дети» и «Пожилые»):**
- Всё из уровня 1.
- Справка об отсутствии судимости (eGov, срок действия — 3 мес., автопометка о протухании и повторный запрос).
- Справки о том, что не состоит на учёте в психоневрологическом и наркологическом диспансерах (eGov).
- Проверка модератором: видеозвонок-интервью 10–15 минут ИЛИ загруженное видео-представление.

**Уровень 3 — Профессионал:**
- Всё из уровня 2.
- Подтверждённые документы об образовании (педагогическое/медицинское) и сертификаты (первая помощь и т.п.).
- 10+ выполненных заказов с рейтингом ≥ 4.7.
- Значок в поиске, приоритет в выдаче.

### 4.2. Флоу получения и проверки документов

**Принцип:** справки загружает сам исполнитель (платформа юридически не может запрашивать их за него — документы eGov выдаются только самому гражданину). Доверие обеспечивается не фактом загрузки, а трёхзвенной проверкой: подлинность документа → живая личность → совпадение ИИН.

**Шаг 1. Загрузка исполнителем:**
- В разделе верификации — пошаговая инструкция получения каждой справки в eGov mobile (с диплинками в приложение eGov), справки выдаются онлайн бесплатно за несколько минут.
- Исполнитель загружает PDF-файлы: справка о несудимости, справки о неучёте в психоневрологическом и наркологическом диспансерах.
- Валидация при загрузке: файл является PDF, содержит QR-код, дата выдачи не старше срока действия.

**Шаг 2. Проверка подлинности (анти-подделка PDF):**
- Каждый электронный документ eGov содержит QR-код/уникальный номер; модератор проверяет документ через официальный сервис проверки eGov — сверяет содержимое с оригиналом на стороне государства.
- MVP: ручная проверка модератором по чек-листу (норматив ~2–3 мин на анкету).
- Этап 1.5 (быстрая автоматизация): автоматическое извлечение QR из PDF и программная проверка по публичной проверочной ссылке eGov; ручная проверка остаётся только для исключений. Это не требует договорной интеграции с госорганами.
- Этап 2 (исследование): «Цифровые документы» eGov (передача документа гражданином по согласию из приложения) и Smart Bridge — при подтверждении доступности для частных компаний.

**Шаг 3. Проверка личности (liveness + сверка с документом):**
- Селфи-проверка с контролем живости (liveness) и сверка лица с фото в удостоверении личности.
- Реализация через коммерческого KYC-провайдера, работающего в РК (Verigram или аналог, используемые банками/МФО). Требования к провайдеру: API для мобильных SDK (iOS/Android), liveness-детекция, распознавание удостоверения РК с извлечением ИИН, хранение/обработка с учётом закона РК о ПДн, стоимость за проверку — закладывается в юнит-экономику онбординга исполнителя.

**Шаг 4. Связка по ИИН (защита от чужих справок):**
- ИИН, извлечённый из удостоверения (шаг 3), должен совпадать с ИИН во всех загруженных справках (шаг 1–2). Несовпадение = автоматический отказ и флаг для модератора.
- Без этой связки схема уязвима: человек с судимостью мог бы загрузить чужие «чистые» справки.

**Сроки действия и повторные проверки:**
- Справка о несудимости считается действительной 3 месяца с даты выдачи (внутренний норматив платформы).
- За 14 и 3 дня до истечения — push/SMS исполнителю «обновите справку»; по истечении профиль автоматически скрывается из поиска до загрузки свежей справки (не удаляется).
- Аналогично для диспансерных справок (норматив — 6 месяцев).

**Согласия и хранение (ПДн):**
- При загрузке документов — явное оформленное согласие на сбор и обработку персональных данных, включая чувствительные (текст согласия — от юриста, фиксация факта: кто, когда, какая версия текста).
- Документы хранятся в отдельном шифруемом контуре; доступ — только у модераторов по ролям, каждый просмотр журналируется (кто, когда, чей документ).
- Заказчику документы не показываются никогда — только статусы («несудимость подтверждена, действительна до ДД.ММ.ГГГГ»).
- Право на удаление: при удалении аккаунта документы удаляются в установленный срок, статусы верификации аннулируются.

### 4.3. Верификация заказчиков
- Телефон (SMS) — обязательно.
- Подтверждение личности (Digital ID) — опционально, даёт значок «проверенный заказчик» (исполнители тоже хотят безопасности: выезд в чужой дом).

### 4.4. Непрерывное доверие (после онбординга)
- Отзывы только по завершённым и оплаченным через платформу заказам.
- Двусторонние оценки (заказчик ↔ исполнитель).
- Жалобы с эскалацией модератору; автоматическая приостановка профиля при жалобе категории «безопасность» до разбора.
- Опция «SOS-кнопка» в активном заказе (этап 2).

## 5. Функциональные требования

### 5.1. Поиск и подбор (заказчик)
- Поиск по: категория услуги, район/геолокация (2GIS-карта), дата и время, срочность («сегодня»), цена/час, уровень верификации, опыт, языки (каз/рус/англ), доп. фильтры по вертикали (возраст ребёнка, опыт с деменцией и т.д.).
- Выдача: карточки с фото, рейтингом, уровнем верификации, ценой, откликом времени ответа.
- Два сценария найма:
  1. **Каталог**: заказчик сам выбирает исполнителя и пишет ему.
  2. **Заявка**: заказчик публикует заказ, релевантные исполнители откликаются (аналог биржи; критично для срочных заказов).
- Сохранённые исполнители («избранное»), повторный заказ в 2 клика.

### 5.2. Профиль исполнителя
- Фото, видео-представление (30–60 сек), описание, опыт, образование, сертификаты.
- Услуги и тарифы (за час / за смену / за месяц), календарь занятости.
- Радиус выезда / районы работы.
- Публичный уровень верификации и дата последней проверки справок.
- Отзывы и рейтинг (разбивка: пунктуальность, отношение, коммуникация).

### 5.3. Заказ и его жизненный цикл
Статусы: Черновик → Опубликован/Отправлен → Принят исполнителем → Подтверждён (предоплата/холд) → В работе (чек-ин исполнителя) → Завершён (чек-аут) → Оплачен → Отзыв.
- Чек-ин/чек-аут по геолокации (по согласию) — фиксация фактических часов для почасовых заказов.
- Отмены: правила и штрафы по времени до начала (настраиваются админом).
- Регулярные заказы: расписание (например, пн/ср/пт 18:00–21:00) с автосозданием заказов.

### 5.4. Коммуникации
- Встроенный чат (текст, фото, голосовые) — до момента оплаты контакты (телефон) скрыты, антидизинтермедиация: маскировка номеров/фильтр обмена контактами в чате.
- Push-уведомления (FCM/APNS), SMS-фолбэк для критических событий (подтверждение заказа).

### 5.5. Оплата
- Платёжные методы: Kaspi Pay, карты (эквайринг местного банка), Apple Pay/Google Pay.
- Модель: холдирование суммы при подтверждении → списание после чек-аута → выплата исполнителю за вычетом комиссии.
- Выплаты исполнителям: на карту/Kaspi, реестр выплат, периодичность — ежедневно/еженедельно.
- Чеки (ОФД) — юридическая проработка: платформа как платёжный агент; статусы исполнителей (самозанятые / ИП) — консультация с юристом на этапе договорной схемы.

**Налоговый и фискальный контур (обновлено, требует подтверждения у налогового консультанта РК):**
- **ЕСП отменён с 1 января 2024 года** — режим действовал 2019–2023 и в расчётах больше не применяется. Актуальный статус для физлиц-исполнителей: самозанятый (единый платёж с социальными отчислениями от дохода) либо ИП. Конкретные ставки уточнить на дату запуска.
- **С 2026 года маркетплейсы, интернет-агрегаторы и банки наделяются функциями налоговых агентов**: удержание и перечисление налога при выплате доходов исполнителям, передача сведений об операциях в налоговый орган. Если это распространяется на нашу модель, из этого следуют требования к продукту:
  - удержание налога при выплате в реестре выплат (сейчас удерживается только комиссия);
  - хранение налогового статуса исполнителя (самозанятый / ИП / не определён) и его ИИН/БИН;
  - регулярная выгрузка сведений о выплатах физлицам в требуемом формате;
  - блокировка выплат исполнителю с неподтверждённым налоговым статусом.
- Ставки удержания, формат и сроки отчётности **не подтверждены первоисточником** — вынести в задачу юристу/налоговому консультанту (см. п. 8.1).
- Для долгосрочных нянь (месячная оплата): этап 2, механика «подписка/зарплатный график» — в MVP только почасовые и посменные оплаты через платформу.

### 5.6. Отзывы и рейтинг
- Отзыв доступен 14 дней после завершения заказа, редактирование 48 часов.
- Ответ исполнителя на отзыв.
- Модерация отзывов (стоп-слова, ручная очередь для оценок 1–2).

### 5.7. Админ-панель
- Очередь верификации (документы, видео-интервью) с чек-листом модератора.
- Управление категориями, тарифами комиссии, промокодами.
- Споры и жалобы: тикеты, статусы, компенсации.
- Аналитика: воронка заказов, GMV, плотность предложения по районам, LTV/повторные заказы.
- Финансы: реестры выплат, сверка с эквайрингом.

### 5.8. Монетизация — гибридная модель по типам заказов

Принцип: способ заработка привязан к типу заказа, потому что поведение пар «заказчик–исполнитель» кардинально разное. С долгосрочных пар деньги берутся в момент знакомства (обход после знакомства неизбежен и считается нормой), с разовых и срочных — комиссия с каждого заказа (обход экономически бессмыслен).

**Тип A. Подбор постоянного исполнителя (няня на полный день, сиделка с проживанием/24-7):**
- Разовый **fee за успешный подбор**, оплачивает заказчик в момент подтверждения найма.
- Ориентир цены: 30–50% месячной ставки исполнителя, т.е. заметно ниже кадровых агентств (у них — от 50–100% месячной зарплаты). Для Астаны при зарплате няни ~250–350 тыс. тг/мес fee ≈ 80–150 тыс. тг. Цифры — ориентир, уточнить исследованием рынка перед запуском.
- В fee включена **гарантия замены**: если исполнитель не подошёл в течение 30 дней — бесплатный повторный подбор. Гарантия оправдывает цену и возвращает заказчика на платформу при неудаче.
- После подбора пара выводится из комиссионной логики: дальнейшие расчёты между ними — напрямую, платформа не претендует. Продолжение оплат через платформу — опционально (даёт историю для рейтинга исполнителя).

**Тип B. Разовые и срочные заказы (бебиситтер «на вечер/сегодня», сиделка почасовая, уход после выписки, компаньон):**
- **Комиссия 15%** с суммы заказа, удерживается с исполнителя при выплате. Оплата — только через платформу (холдирование → чек-аут → выплата).
- Это основной комиссионный поток: в срочных заказах каждый раз нужен новый/свободный человек, обхода нет по природе спроса.
- Механики удержания оплат внутри: страховка/гарантия действует только для платформенных заказов; отзывы и рейтинг начисляются только за оплаченные через платформу заказы; поддержка при споре — только по платформенным заказам.

**Тип C. Повторные нерегулярные заказы (та же бебиситтер раз в 1–2 недели):**
- Та же комиссия 15%. Частичная утечка в прямые расчёты признаётся и **закладывается в финмодель** (консервативно: до 40–50% повторных пар уходит в обход после 3–5 заказов). Не штрафуется — борьба ведётся ценностью (удобство оплаты, история, отзывы), а не запретами.

**Отложено на этап 2+ (после набора плотности):**
- Платное продвижение анкет и подписка «Pro» для исполнителей — включать только когда в основных районах появится реальная конкуренция анкет (десятки исполнителей на район); на пустом каталоге не работает. Ограничение: буст влияет на порядок внутри одного уровня верификации, но никогда не поднимает менее проверенного исполнителя над более проверенным.
- Подписка заказчика (сниженная комиссия, расширенные фильтры, приоритетная поддержка).
- B2B-пакеты (уход как корпоративный бенефит) и партнёрские доходы (страхование, обучение исполнителей).

**Ключевая метрика здоровья модели:** доля повторных потребностей, с которыми заказчик возвращается в приложение (новая ситуация → снова открыл поиск), а не удержание конкретной пары «семья–няня».

**Что платформа не монетизирует принципиально:** верификацию и справки. Проверка безопасности бесплатна для исполнителя (или по себестоимости) — безопасность не может быть платной опцией.

## 6. Нефункциональные требования

- **Платформы:** iOS, Android (единая кодовая база — Flutter или React Native; финальный выбор — отдельное решение), веб-версия для SEO-каталога исполнителей (важный канал органики) и админка (web).
- **Backend:** REST/JSON API; PostgreSQL; очередь задач для уведомлений и автоматики статусов; S3-совместимое хранилище для медиа и документов (документы — отдельный шифруемый бакет).
- **Карты и гео:** 2GIS SDK (приоритет для КЗ), геокодинг адресов.
- **Персональные данные:** соответствие Закону РК «О персональных данных»: согласия, хранение на территории РК (выбор хостинга — с учётом требования локализации ПДн), право на удаление, журналирование доступа к документам.
- **Безопасность:** TLS, шифрование документов at rest, RBAC в админке, rate limiting, аудит-лог действий модераторов.
- **Нагрузка (MVP):** до 10K MAU, до 500 одновременных пользователей — без специальной оптимизации, но с горизонтально масштабируемой архитектурой.
- **Доступность:** SLA 99.5% для MVP.

## 7. Этапность

### Этап 1 — MVP (цель: 3–4 месяца разработки)
- Вертикали: дети (бебиситтер, няня), пожилые (сиделка, компаньон).
- Верификация уровней 0–2 (модерация ручная, справки проверяются модератором).
- Каталог + заявки, чат, заказы почасовые/посменные, оплата (Kaspi Pay + карты), отзывы.
- Монетизация: fee за подбор постоянных исполнителей (тип A) + комиссия 15% с разовых/срочных заказов (типы B/C). Флоу «подбор постоянной няни» с гарантией замены — обязательная часть MVP.
- Один город (Астана), 2 языка.
- Админ-панель: верификация, споры, финансы (минимум).

### Этап 2
- Питомцы (Rover-механика), уровень верификации 3, регулярные расписания, подписки, SEO-веб, SOS-кнопка, автопроверка справок по API, Алматы.

### Этап 3
- Вертикаль «Инвалидность» + интеграция с госпрограммами, медпатронаж через лицензированных партнёров, месячные контракты нянь, остальные города.

## 8. Открытые вопросы (требуют решения до старта разработки)

1. **Юридическая схема: информационный сервис или платёжный агент?** — ключевой вопрос, определяет архитектуру денежного контура.

   **Информационный сервис**: платформа только сводит стороны, деньги идут напрямую между заказчиком и исполнителем, платформа выставляет чек лишь за свою услугу. Юридически проще, но ломает половину механик ТЗ: холдирование (5.5), отзывы только по оплаченным заказам (4.4), штрафы за отмену (5.3), гарантию замены (5.8), споры и компенсации (5.7). Антидизинтермедиация тоже теряет смысл — контакты всё равно нужны для расчёта.

   **Платёжный агент**: платформа принимает деньги заказчика в пользу исполнителя, удерживает комиссию, перечисляет остаток. Требует агентских договоров с исполнителями, решения о том, кто пробивает чек за услугу исполнителя, и соответствия Закону РК «О платежах и платёжных системах».

   **Позиция на текущий момент:** целевая схема — платёжный агент, иначе продукт теряет ядро доверия. При этом гибридная монетизация (5.8) допускает поэтапный запуск:
   - **тип A (fee за подбор)** — платформа продаёт собственную услугу, транзита чужих денег нет, работает и в простой схеме;
   - **типы B/C (комиссия с заказов)** — требуют агентской обвязки.

   То есть можно выйти на рынок на типе A, пока готовится договорная схема для B/C. В реализации это разделение уже заложено и включается настройкой.

   **Вопросы юристу и налоговому консультанту:**
   1. Нужен ли статус платёжного агента, или достаточно агентского договора с исполнителями при приёме денег через банк-эквайер?
   2. Кто пробивает фискальный чек за услугу исполнителя — платформа как агент или исполнитель сам?
   3. Подтвердить обязанности налогового агента с 2026 года: ставка удержания при выплате физлицу, формат и сроки отчётности.
   4. Чем оформляется удержанный штраф за отмену — доход платформы или компенсация исполнителю?
   5. Статус исполнителей: самозанятый или ИП; **ЕСП отменён с 01.01.2024** и в схеме не используется.
2. Доступность API госсервисов (проверка справок) для частной компании — либо остаёмся на ручной проверке QR.
3. Страхование ответственности исполнителя (партнёрство со страховой) — сильный дифференциатор, но не блокер MVP.
4. Выбор мобильного фреймворка (Flutter vs React Native) и состава команды.
5. Холодный старт: стратегия набора первых 100 верифицированных исполнителей до публичного запуска (реферальные бонусы, партнёрство с педколледжами/медколледжами, перехват из агентств).
