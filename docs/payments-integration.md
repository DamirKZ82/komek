# Подключение эквайринга

Платёжный контур написан провайдер-агностично: код приложения ходит только через
интерфейс `PaymentGateway` ([backend/app/services/payment_gateway.py](../backend/app/services/payment_gateway.py)).
Пока `PAYMENT_API_URL` не задан, работает песочница — она не ходит в сеть и подтверждает
любой платёж. **В production песочница запрещена**: приложение упадёт при старте платежа,
чтобы заказы не оказались бесплатными.

## Что заполнить в `.env`

```
PAYMENT_API_URL=https://api.acquirer.kz/v1
PAYMENT_API_KEY=...
PAYMENT_WEBHOOK_SECRET=whsec_...
PAYMENT_WEBHOOK_URL=https://api.komek.kz/api/v1/webhooks/payments
```

## Что проверить у конкретного эквайера

`HttpPaymentGateway` использует типовые пути и имена полей. Сверьте с документацией
провайдера и поправьте при расхождении — это единственное место, которое меняется:

| Операция | Путь в коде | Что уточнить |
|---|---|---|
| Холд | `POST /payments/authorize` | имя флага «только авторизация» (`capture: false`) |
| Списание | `POST /payments/{id}/capture` | допускает ли частичное списание |
| Возврат | `POST /payments/{id}/refund` | допускает ли частичный возврат |
| Выплата | `POST /payouts` | формат реквизитов исполнителя |

Ответ разбирается по полям `status`, `id`/`transaction_id`, `card_mask`,
`confirmation_url`, `error_message`. Статусы `pending`/`processing` означают, что итог
придёт вебхуком — заказ в этом случае не переводится в «оплачен» синхронно.

Идемпотентность: в каждый запрос уходит заголовок `Idempotency-Key`
(`hold-<order_id>`, `capture-<order_id>`, `cancel-refund-<order_id>`, `payout-<payout_id>`),
поэтому ретраи не создают двойных списаний.

## Вебхуки

Эндпоинт: `POST /api/v1/webhooks/payments`.

Проверяется подпись:

```
signature = HMAC_SHA256(secret, "<X-Timestamp>." + <сырое тело запроса>)
```

Заголовки: `X-Signature` (hex) и `X-Timestamp` (unix-время). События старше
`PAYMENT_WEBHOOK_MAX_AGE_SECONDS` (по умолчанию 5 минут) отбрасываются — защита от replay.
Если у провайдера другая схема подписи, меняется только `_verify_signature`
в [backend/app/api/v1/webhooks.py](../backend/app/api/v1/webhooks.py).

Обрабатываемые типы: `payment.authorized`/`payment.hold`, `payment.captured`/`payment.succeeded`,
`payment.refunded`/`payment.reversed`, `payment.failed`/`payment.declined`.
Повторная доставка того же `event_id` не меняет состояние дважды — события пишутся
в таблицу `webhook_events`.

## Денежные сценарии

- **Подтверждение заказа** (типы B/C) — холд на расчётную сумму.
- **Чек-аут и оплата** — списание фактической суммы; если холд был больше, разница
  возвращается заказчику автоматически.
- **Отмена заказчиком** — возврат за вычетом штрафа по правилам из админки,
  штраф списывается в пользу платформы.
- **Отмена исполнителем или платформой** — полный возврат, без штрафа.
- **Выплаты исполнителям** — реестр в админке, перевод через `payout()` эквайера.

## Сверка

`GET /api/v1/admin/reconciliation` и вкладка «Финансы» в админке показывают расхождения:
заказы со статусом «оплачен» без успешного списания, зависшие холды по закрытым заказам,
отклонённые платежи. Это то, что разбирается вручную после сбоев сети или отказов эквайера.
