# Подключение SMS и KYC

## SMS

Провайдер выбирается настройкой `SMS_PROVIDER`:

| Значение | Когда использовать |
|---|---|
| `log` | Разработка: сообщение пишется в лог, SMS не тратятся. **Запрещено в production** — иначе коды входа уходили бы в лог и войти было бы невозможно. |
| `mobizon` | [Mobizon](https://mobizon.kz/help/api-docs/message) — популярный шлюз в РК. Реализован точно по документации. |
| `http` | Универсальный JSON-POST под любого другого провайдера. |

```
SMS_PROVIDER=mobizon
SMS_API_KEY=...
SMS_SENDER=Komek
```

Подпись отправителя (`SMS_SENDER`) у операторов РК проходит модерацию — заказывайте
заранее, иначе сообщения уйдут с подписью по умолчанию или будут отклонены.

### Особенности Mobizon

- Номер передаётся **без `+`**: `77011234567`. Перестановка делается в адаптере.
- Ответ: `{"code": 0, "data": {...}, "message": "..."}`, где `code = 0` — успех.
  Ненулевой код означает отказ: он попадает в журнал, но не роняет сценарий.
- Статусы доставки запрашиваются методом `GetSMSStatus` (до 100 идентификаторов за раз)
  и приводятся к нашим: `DELIVRD` → доставлено, `EXPIRED` → истекло,
  `UNDELIV`/`REJECTD`/`DELETED` → ошибка.

### Журнал отправок

Каждая отправка пишется в `sms_messages`: телефон, назначение (`otp`, `notification`),
провайдер, статус, идентификатор у провайдера, ошибка. **Текст сообщения не хранится** —
в нём код входа. Без журнала невозможно разобрать обращение «код не пришёл».

Статусы доставки подтягивает воркер:

```bash
python -m app.workers.sms
```

Планировать раз в 5–10 минут.

## KYC (проверка личности)

Публичной документации у Verigram нет — API выдаётся по договору (`sales@verigram.ai`).
Поэтому адаптер написан по типовой для отрасли схеме; при подключении меняются
URL и имена полей в `_parse_result`, остальное остаётся.

```
KYC_API_URL=https://api.verigram.ai/v1
KYC_API_KEY=...
KYC_WEBHOOK_SECRET=...
KYC_WEBHOOK_URL=https://api.komek.kz/api/v1/webhooks/kyc
```

Без `KYC_API_URL` работает заглушка, которая подтверждает любую сессию.
**В production она запрещена** — иначе кто угодно получил бы значок «проверенный».

### Флоу (три шага)

1. `POST /me/identity/session` — бэкенд создаёт сессию у провайдера и отдаёт клиенту
   `session_id` и `client_token`.
2. Мобильный SDK проводит liveness и съёмку удостоверения по `client_token`.
3. `POST /me/identity` с `session_id` — личность подтверждается **по результату от
   провайдера**, а не по словам клиента.

Результат приходит вебхуком `POST /api/v1/webhooks/kyc` (подпись HMAC, как у платежей);
если вебхук не успел, бэкенд сам опрашивает провайдера при подтверждении.

### Что защищено

- Клиент не может объявить себя проверенным: он передаёт только `session_id`,
  а исход берётся из сессии, подтверждённой провайдером.
- Чужая сессия не подходит — проверяется владелец.
- Использованная сессия не применяется повторно (`consumed_at`).
- Сессия живёт `KYC_SESSION_TTL_MINUTES` (по умолчанию 30 минут).
- Один ИИН — один аккаунт: повторная привязка отклоняется (`iin_already_used`).
- Исполнителю проверяется возраст 18+ (п. 4.1 ТЗ).

### Что даёт подтверждение

- Заказчику — значок «проверенный», видимый исполнителю в диалоге (п. 4.3 ТЗ):
  исполнителю тоже важно знать, к кому он едет.
- Исполнителю — уровень 1 и ИИН для сверки со справками (шаг 4 флоу, п. 4.2 ТЗ).
